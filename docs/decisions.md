# Decision log

The System Design Document (SDD v1.1) is the original design. [`prd.md`](../prd.md) amends it (design decisions
D-01…D-08) and listed the questions left open; [`plan.md`](../plan.md) records, phase by phase, how each slice was
built. This page is the one place that says what was decided, when, and why — in short, with a link to the detail.

## Open Question 7 — how the SDD is kept up to date

**Decision (Phase 15): the PRD stays the amendment record; there is no SDD v1.2.** Where the PRD and the SDD disagree,
the PRD wins (README, *Documents*). The PRD's §8 lists every deviation from the SDD, each phase's *Decisions taken*
table in `plan.md` records the finer choices, and this log indexes them.

*Why:* a v1.2 would copy the SDD to change a handful of paragraphs, and two long documents that must agree is the
problem the PRD already solves. The code, its tests and these three documents are what a reader checks; a fourth
copy of the design would only drift.

## Phase 15 decisions (release sweep)

| Topic | Decision |
|---|---|
| Customers and equipment | Reads are **office-only** (Admin, Manager, ServiceStaff), like the pages that show them. Until now any signed-in role could list the customer directory; a Technician sees a customer and machine only through their own job (BR-02), and the warehouse has no use for them. |
| Deny by default | A **fallback authorization policy** requires a signed-in user on any endpoint without its own rule. Only login and the two health checks are public, and a test pins that list. |
| AC-11 over the whole surface | `EndpointAccessTests` now has a row for **every** route (56), and a test compares the table with the routes the app actually maps, so a new endpoint without a row fails the build. |
| CORS | None needed for the shipped app (same origin through nginx). Outside Development the allowed origins come from `Cors:AllowedOrigins`, empty by default; the hard-coded localhost origins are gone. |
| Browser hardening | nginx sends a Content-Security-Policy (same origin only; `blob:`/`data:` for the signature, photos and PDFs), `X-Content-Type-Options`, `X-Frame-Options: DENY`, a referrer policy and a permissions policy. The API adds HSTS when it terminates HTTPS itself (not in Docker, where nginx speaks plain HTTP). |
| Dependencies | Upgraded to clear every advisory: Vite 8, Vitest 5, `@vitejs/plugin-react` 6, React Router 7 (library mode, no code change), ASP.NET Core/EF Core 8.0.31 patches and newer test tooling. `npm audit` and `dotnet list package --vulnerable --include-transitive` report nothing. |
| Secrets | gitleaks over the **full history** finds only Azurite's published development key (accepted in `.gitleaksignore`); CI now runs the same scan on every push. |
| Pagination | **Not added.** Every list is bounded by the demo's scale (tens to a few hundred rows) and the long ones have server-side filters (requests and jobs by status, the ledger by part, type, job and date). Paging changes every list's contract and page, so it is on the V2 list rather than half-done now. |
| Seed | Grown to the PRD's scale — **10 customers, 30 equipment** — with no jobs on the new rows, so every hand-computed dashboard figure is unchanged. A test proves the seed has a record in every reachable state. |

## After Phase 15

| Topic | Decision |
|---|---|
| .NET version | **Moved from .NET 8 to .NET 10** (LTS, supported to November 2028) before .NET 8 support ends on 10 November 2026. .NET 9 was skipped: its support ends on the same day. The two projects target `net10.0`, the ASP.NET Core/EF Core packages are 10.0.12, the API image is built on `sdk:10.0`/`aspnet:10.0` and CI installs `10.0.x`. Swashbuckle stays on 6.6.2 (the newer major moves to OpenAPI v2 for no gain here). No code changes were needed. |
| Reverse proxy | **`UseForwardedHeaders`, first in the pipeline**, trusting `X-Forwarded-For`/`-Proto` only from hops in `ForwardedHeaders:KnownNetworks` (the private ranges by default: nginx on the compose network, a platform ingress). It walks back past every trusted hop to the first outside address, so the API sees the real caller and a forged entry in front of it is ignored. |
| Connection string | **Checked at startup**, like the JWT key and the storage connection: a missing `ConnectionStrings:DefaultConnection` stops the API with a hint instead of failing on the first query. |
| Unhandled exceptions | The hand-written middleware became **an `IExceptionHandler` under `UseExceptionHandler`**: the framework clears a half-written response and handles client disconnects, and the handler refuses to write once `Response.HasStarted`. Same 500 body as before (ProblemDetails with a `traceId`), now covered by a test. |
| Database logins | **The API no longer connects as `sa` in Docker.** `scripts/sql/create-logins.sql`, run as `sa` by a one-shot `db-init` service, creates the database and two logins: the app's (dbo data read/write, the report-number sequence, and `db_ddladmin` because the demo migrates on startup; no server rights) and a `db_datareader`-only one behind the optional `ConnectionStrings:AiReadOnly`, so SQL Server refuses an AI write even past the in-app `ReadOnlyGuard`. `DemoApiFactory` runs the same script, so the demo tests run on these logins. A production deployment would migrate with a separate login and drop `db_ddladmin` from the app's. |
| Dependency updates | **Dependabot**, weekly and grouped (ASP.NET Core/EF Core together, test tooling, web minor+patch), for NuGet, npm, GitHub Actions and the Dockerfiles. Major versions of the .NET packages and images are ignored: they arrive with a planned .NET upgrade, like this one. |
| Folders | `DatabaseHealthCheck` moved to `HealthChecks/` and the exception handler to `ErrorHandling/`; neither was middleware. |
| Ledger immutability in the database | **A trigger and a DENY.** `TR_InventoryTransactions_Immutable` (an `AFTER UPDATE, DELETE` trigger, added by a migration) throws error 50009 when a statement changes a ledger row, so BR-09 holds for every login, in tests (which run as `sa`), on LocalDB and in Azure alike. On top of that the ledger lives in its own `ledger` schema (migration `LedgerSchema`, which rebuilds the table there with the same ids: `ALTER SCHEMA ... TRANSFER` needs CONTROL, which the app login does not have), which `create-logins.sql` creates before any migration runs and on which it grants the app login only `SELECT`, `INSERT` and `REFERENCES` and `DENY`s `UPDATE` and `DELETE`. A schema-level permission exists before the table does, so it binds from the first row on a fresh volume (an object-level DENY could not, which is why the trigger came first); SQL Server refuses with error 229 before the trigger is reached. The DENY binds only that login (`sa`/dbo and Azure's server admin ignore it, hence the trigger stays). A login with DDL rights (the demo's `db_ddladmin`) could still move the table out or disable the trigger; a production app login without DDL rights could do neither. EF Core is told about the trigger (`HasTrigger`), so it saves ledger rows without an `OUTPUT` clause. |
| Part `RowVersion` | Its comment said it stopped two technicians issuing the same stock; that has been the conditional `UPDATE` since Phase 6. It now says what it does: the conflict token for catalogue edits, bumped by every stock movement. |
| Equipment serial numbers | **Unique per brand** (`IX_Equipment_Brand_SerialNumber`) instead of globally: manufacturers number independently, so two brands can share a serial. The index has no `Brand IS NOT NULL` filter, so unbranded equipment cannot share one either, and the service stores a blank brand as none and compares case-insensitively (the database collation). Looser than before, so existing data needed no change. |
| Seeded users and roles | `DbSeeder` and `DemoSeeder` **check `AddToRoleAsync`** and create each account and its role in one transaction; a refused step stops startup. Before, a failed role assignment left an admin with no role that the next start would skip (the email exists). `UserService` now also checks the role and security-stamp results of an edit and rolls the edit back if one fails. |
| Timestamps | **`DateTime`, documented as UTC everywhere**, not a move to `DateTimeOffset`. Every value is written from `DateTime.UtcNow` or `TimeProvider.GetUtcNow()`, the API converts to MYT only through `ReportRules.MytOffset` (reports, dashboards), and the web app reads the API's timestamps as UTC. Converting every timestamp column, its DTOs and the tests would change the API's JSON for no behaviour gain in a single-time-zone business; `DateTimeOffset` is the choice for a version that spans time zones. |
| Entity configurations | **`ApplyConfigurationsFromAssembly`** replaces the nine hand-listed `ApplyConfiguration` calls, so a new configuration cannot be forgotten. The generated model was unchanged by the switch. |
| Schema changes on real data | **Expand and contract** from now on: add the new shape alongside the old, backfill, switch the readers, and drop the old shape in a later release, never a drop or rename in one step. Until now the database only ever held demo data that a reseed recreates, so this had not mattered. |
| Sessions and refresh tokens | **15-minute access tokens plus a rotating refresh token in an `HttpOnly` cookie** (was: one 60-minute token in `localStorage`). The access token is in memory only, so a script injected into the page cannot carry it off for later, and the cookie cannot be read by script at all. `SameSite=Strict` and the `/api/auth` path keep the cookie off other sites' requests and off every other endpoint, so cookie auth brings no CSRF exposure to the data API, which still takes only the bearer token. Refresh tokens are stored as SHA-256 hashes with the user's security stamp; each refresh rotates the token without extending the 12-hour session. A rotated token presented again within 30 seconds is a second tab racing the first and still gets a session; later, it means a copy leaked, and every session of that user ends. The web app restores the session from the cookie on load, renews a minute before expiry, and retries a call that meets a 401 once after a refresh. |
| Login rate limit | **20 attempts a minute per client address** on `POST /api/auth/login` (`Auth:LoginPermitsPerMinute`), alongside Identity's per-account lockout, which alone cannot slow one address guessing across many accounts. The address comes through `UseForwardedHeaders`, so behind nginx it is the caller's, not the proxy's. 20 rather than 10 so an office behind one NAT, or the smoke test, does not trip it. |
| Login timing | An unknown or inactive account **still verifies the password against a dummy hash**, so it takes as long as a wrong password and response times do not reveal which emails have accounts. A test counts the hash verifications. |
| Role names in `[Authorize]` | **`AppRoles` constants everywhere** (`Roles = $"{AppRoles.Admin},{AppRoles.Manager}"`), as the newer controllers already did; a typo is now a compile error instead of a silent 403. Named policies were not needed: the role lists are short and read clearly at the endpoint. |
| `/me` | **Moved into `AuthService.GetCurrentUserAsync`**, so `AuthController` no longer reaches into `UserManager` and every auth endpoint goes through the service. |
| Request → jobs | **One-to-many** (`ServiceRequest.WorkOrders`). It was modelled one-to-one while the filtered unique index already allowed a cancelled job plus a live one, so a request read after a cancel and reassign had two candidates for one navigation. Cancelled jobs now stay listed with their request; the DTO names the live job (`workOrderId`) and the cancelled ones (`cancelledWorkOrderIds`). No schema change was needed. |
| Who approved a job | **`WorkOrder.ApprovedByUserId`**, set in the same conditional `UPDATE` as `ApprovedAt` and shown on the timeline, like who cancelled. Jobs approved before it existed keep a null approver: there is no record to backfill from. |
| Approval and the report | **Approval requires a generated service report.** An Approved job is final and its report is the customer-facing record, so approving one without it left the locked job undocumented. The check runs before the transition (a clear `400`) and again in the `UPDATE`'s `WHERE`. The Approve button stays disabled with a hint until the report exists. The "approved without a report may get exactly one" rule remains for older data. |
| Cancelling and issued parts | **Cancelling returns them to stock**, in the cancel's transaction, one `Return` ledger row per line by the Manager. Before, the parts stayed issued to a locked job that nobody could return them from, so stock was lost unless the warehouse noticed. A part that really was fitted is written off with an Adjustment, which is the rarer case. |
| `WorkOrderStatus.New` | **Removed.** Assignment creates a job as `Assigned`; nothing ever produced `New`, but it appeared in the state machine (as cancellable), the dashboards' status series and the UI's status lists. Statuses are stored as text, so no data changed. |
| rowVersion parsing | **One global action filter** (`RowVersionFilter`) checks every request implementing `IRowVersionRequest` and answers a malformed or missing token with the same `400` before the action runs, replacing seventeen copies of the same check. A filter rather than a model binder, so the DTOs keep a plain string and the multipart uploads are covered too; a test fails if a request DTO with a `RowVersion` skips the interface. |
| Paging | **Still V2** (see Phase 15). When it comes, the service-request and work-order lists go first, with list DTOs that drop the detail-only fields. |
| Photo metadata | **Stripped on upload, orientation kept** (`PhotoMetadata`). Phones write the GPS position, time, camera and owner into a photo, and photos are shown to every office role and put in a customer-facing PDF. The JPEG's segments before the image data are filtered (EXIF is replaced by a minimal block holding only the orientation; XMP, IPTC, comments, maker data and JFXX thumbnails are dropped; JFIF, the ICC profile and Adobe's colour-transform marker stay because they change how the picture looks), the image data is copied byte for byte, and anything after the end-of-image marker (the extra pictures of a multi-picture file) is cut off. A PNG loses its text, time and EXIF chunks the same way. Nothing is decoded or re-encoded, so there is no quality loss and no imaging library. A file whose structure cannot be followed is refused (400) rather than stored with its metadata. Photos stored before this keep theirs. |
| WebP photos | **Refused by the API, converted by the web app.** A PDF has no filter for WebP, so a WebP photo could never appear in the service report, and decoding it on the server would need an imaging library. The API still recognises WebP from its bytes but answers with its own message; the web app redraws a WebP as a JPEG before uploading (as it already did for HEIC and oversized photos). WebP photos stored before this stay listed but not pictured. |
| Text beyond Latin-1 in reports | **An embedded subset of Noto Sans SC** (SIL OFL 1.1), written by hand like the rest of the PDF: `TrueTypeFont` reads the font's tables and writes a subset holding only the glyphs a report uses, and the document embeds it as a Type0/CIDFontType2 font with a ToUnicode map (so copying text out of the PDF works). Helvetica still draws everything WinAnsi can hold, so a Latin-only report is byte-for-byte what it was and embeds no font; only characters outside WinAnsi go to the fallback. It covers Chinese, Greek, Cyrillic and some Latin Extended; scripts that need shaping (Arabic, Tamil, Thai) and the Latin letters it lacks (e.g. ő, ł) still print as `?`. It has one weight, so bold is drawn by also stroking the outline. The font is a static, unhinted regular instance (10 MB, built by `Fonts/make_font.py`) compiled into the API assembly and read only when a report first needs it; a report with a Chinese customer name grows by about 15 KB. A library was not needed: the PDF side is about 300 lines, and every library option still needed the same font file. |
| Claiming a job for a change | **One helper, `JobClaims.ClaimInProgressJobAsync`**, for the parts and photo services (they had identical private copies; the photo one took an extra condition). Same no-op `UPDATE … WHERE owner AND InProgress AND RowVersion = @rv`, optionally with a further condition such as the photo limit. |
| Orphaned files | **Swept on a timer inside the API** (`OrphanFileCleanupService`, `Storage:OrphanCleanup`): ten minutes after startup and then every six hours, files under `work-orders/` that no photo, signature or report row names are deleted once they are a day old. Upload-then-record means a lost commit or a failed cleanup delete leaves a file behind, never a row without its file; the day's grace means a file whose row is still being written is never touched (the API refuses a `MinimumAge` under an hour). Deletes are idempotent, so several instances sweeping at once is harmless; a failed sweep is logged and retried at the next tick. A timer in the API rather than a separate job keeps the deployment at two containers; Azure Container Apps scales to zero, so on the demo it runs only while the app is awake, which is enough for files that only accumulate when it is in use. |
| Streaming photo uploads | **Not now; buffered, with a known trigger.** A photo is at most 8 MB; ASP.NET spools the multipart body to a temporary file past 64 KB, and the API then holds the photo and its stripped copy in memory only for the request (about 16 MB at most per upload in flight). A field team uploading one photo at a time per technician stays far below the container's memory. Streaming would mean reading the multipart section directly (form binding off), detecting the type from the first bytes, stripping metadata as a pass-through stream (it only rewrites the segments before the image data and drops what follows the end marker, so it can work in one pass) and staging the blob in blocks. It becomes worth it if uploads in flight times 16 MB approaches the container's memory (for example dozens at once on a 1 GB container) or if the size limit is raised for video. |
| API types | **Generated from the OpenAPI document.** Every JSON endpoint declares its response type (`[ProducesResponseType<T>]`); the document marks what can be null from the C# nullable annotations and every response property as required (the API always writes them all). It is checked in as `src/SarawakBizOps.Api/openapi.json`, and `OpenApiDocumentTests` fails when it no longer matches the API. `npm run gen:api` turns it into `src/api/schema.d.ts`, and `src/types` aliases those types, narrowing status and priority strings to the app's unions. CI regenerates the types and fails on any difference. The request bodies the app builds stay hand-written, but `src/types/requestContract.ts` makes the build fail if one no longer fits its request schema. |
| Lint and formatting | **ESLint (typescript-eslint, `react-hooks`) and Prettier**, both in CI (`npm run lint`, `npm run format:check`). The hooks rules are the classic two (`rules-of-hooks`, `exhaustive-deps`) as errors. The React Compiler rules in `react-hooks` 7's preset are off: they target code written for the compiler, and they flag the plain fetch-in-effect pattern every page uses. Prettier keeps the existing style (no semicolons, single quotes, 120 columns), so its one-off reformat changed layout only. |
| Timestamps on the wire | **Every DateTime is sent with its `Z`** (`UtcDateTimeConverter`). EF Core reads `datetime2` back as Unspecified, which System.Text.Json wrote with no offset, so each client had to know to read it as UTC. The web app still treats an offset-less time as UTC as a fallback. Reading request bodies is unchanged. |
| The access token in the web app | **The API client holds it and attaches it**; no page or API function takes a token any more. Only the three session calls (login, refresh, logout) are marked `anonymous`. `AuthContext` no longer exposes the token at all. |
| HttpOnly cookie sessions | **Considered; not adopted.** The refresh token is already an `HttpOnly`, `SameSite=Strict` cookie limited to `/api/auth`, and the 15-minute access token lives only in memory, so script can read neither from storage. Moving the access token into a cookie as well would stop injected script from reading it, but that script could still call the API as the user while the page is open, which is the real damage. In exchange, every endpoint would accept a cookie, so every mutating endpoint would need anti-forgery tokens, and the Vite dev server would need credentialed CORS. Revisit if the app ever loads third-party script, or if a native client needs the same session. |
| Accessibility checks | **axe-core in Vitest** (`Accessibility.test.tsx`): 21 pages across every role, with realistic data, against the WCAG 2.1 A and AA rules, on every CI run. jsdom does no layout, so colour contrast still needs the browser sweep. Adding it caught that the sign-in and not-found pages had no heading; their titles are now `h1`. |
| Offline technicians | **Planned** in [offline-plan.md](offline-plan.md): a service worker for the app shell, an IndexedDB copy of the technician's jobs, and an outbox of queued actions replayed in order with idempotency keys. Not built yet. |
